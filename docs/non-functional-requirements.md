# 予約管理システム 非機能要件定義書

- 版: 1.5（2026-08-07 更新。段階0〜5完了・デプロイ運用の実態を反映）
- 対象: `docs/requirements.md` 版 2.0 / `docs/design.md` 版 1.6
- 実装粒度は `docs/detailed-design.md` を参照

要件書 7章の非機能要件を、**測れる形・判定できる形**に展開したもの。
要件書と食い違ったときは要件書を正とし、こちらを直す。

---

## 1. この文書の考え方

このシステムは**共用レンタルサーバー上で動く、1事業者・月数百件規模のデモ兼業務システム**である。
高可用・高性能を狙う環境ではない。したがって非機能要件は次の順で優先する。

1. **壊れたことが分かる**（検知・ログ・監査）
2. **壊れても直せる**（再実行・復旧手順）
3. **壊れにくい**（性能・可用性）

性能や冗長化に投資しても、閲覧者にも発注者にも違いが見えない。
逆に「在庫がズレたまま誰も気づかない」は業務価値を直接損なう。**検知と復旧を上に置く。**

---

## 2. 前提となる環境制約

| 制約 | 内容 | 非機能への影響 |
|---|---|---|
| 実行環境 | Xserver 共用（スタンダード） | 冗長化・オートスケール不可 |
| 常駐プロセス | 立てられない | キューは cron 起動。最大1分の遅延を許容 |
| ミドルウェア | Redis 不可 | キュー・キャッシュ・セッションは database ドライバ |
| 監視基盤 | APM なし | 監視はダッシュボード・通知・外形の死活監視で代替 |
| デプロイ | GitHub Actions から SSH/rsync で転送 | ゼロダウンタイム構成は取らない |

**これらは変更しない前提。** 環境を変える判断をする場合は本書ごと見直す。

## 3. 性能

### 3.1 目標値

| 対象 | 目標 | 測り方 |
|---|---|---|
| 顧客照会画面（C-1・C-2） | 応答 1.0 秒以内 | 本番 URL で手動計測 |
| 管理画面の一覧（A-3） | 応答 2.0 秒以内（50件/ページ） | 同上 |
| Shopify Webhook 応答 | **5秒以内に 200**（必達） | Shopify 管理画面の配信ログ |
| 手動登録の完了 | 5秒以内（Shopify API 同期呼び出しを含む） | 手動計測 |
| キュー投入から実行まで | 最大 1 分 + 実行時間 | `jobs` テーブルの滞留で確認 |

Webhook の 5 秒だけが外部都合の必達要件で、それ以外は目安。
**5秒を守るために本処理をキューへ逃がす**設計（設計 5.1）が、この目標に対応している。

計測は**本番 URL に対して連続5回行い、中央値で判定する**。初回のキャッシュ未構築を避けるため
1回目は捨てる。時間帯による差は追わない。目安値である以上、条件を固定して比較できれば足りる。

### 3.2 想定負荷

- 月間予約件数: 数百件
- 同時利用者: 数名（スタッフ）＋デモ閲覧者
- Webhook 受信: 1日あたり数十件以下
- ピーク: 講座公開直後に購入が集中する程度

この規模では**インデックス設計以上のチューニングを行わない**。
N+1 の回避と、検索対象カラム（`slots.starts_at`, `reservations.code`,
`reservations.email`, `reservations.status`）へのインデックス付与までを実施範囲とする。

### 3.3 やらないこと

キャッシュ層の導入、DB のレプリケーション、CDN、画像最適化基盤は対象外。
規模が理由であり、必要になった時点で追加できる構成にしておく。

## 4. 可用性・信頼性

### 4.1 目標

| 項目 | 目標 |
|---|---|
| サービス稼働 | 共用サーバーの提供水準に準じる（独自の SLA は置かない） |
| 計画停止 | 許容。デプロイ時の瞬断を含む |
| RPO（許容データ損失） | 24 時間（日次バックアップ） |
| RTO（復旧目標時間） | 24 時間 |

デモ環境は**日次でデータを初期化する**性質上、業務データの永続性要求が本番業務システムより低い。
ただし `audit_logs` はリセット対象外（要件 7.4）のため、バックアップの主対象はここになる。

### 4.2 障害時の振る舞い

| 障害 | 振る舞い | 復旧 |
|---|---|---|
| Shopify API 停止 | 手動登録は失敗し予約を作らない。キャンセルは受け付け、在庫戻しはキューに滞留 | 復旧後にジョブが再実行される |
| SMTP 停止 | 業務処理は継続。`mail_logs.status=failed` に記録 | 管理画面から手動再送（設計 7.1） |
| キュー滞留 | 予約登録・メールが遅延。業務データは失われない | cron 復旧で自動消化 |
| cron 停止 | キュー消化・日次バッチ・**即時通知のすべてが止まる**。画面からの操作は動く | 外形監視の途絶で検知し、cron を再設定 |
| DB 障害 | 全機能停止 | バックアップから復元 |

**共通方針: 業務処理を外部サービスの都合で失敗させない。** ただし
**在庫の押さえ（手動登録）だけは例外**で、失敗時は予約を作らない（定員超過を防ぐため）。

**cron 停止だけは自力で検知できない。** 通知もバッチも同じ cron に乗っているため、
止まったこと自体を内部から知らせる手段がない。ここだけ外部からの死活監視で補う（6.3）。

### 4.3 データ保全

- DB: 日次で論理バックアップ（サーバーの自動バックアップ機能を利用）
- 保持世代: 7 世代
- 復元手順を `docs/operations.md` に記載し、**段階5までに一度復元を試す**

## 5. セキュリティ

### 5.1 実装する対策

| 領域 | 対策 |
|---|---|
| 通信 | 全ページ HTTPS。HTTP は 301 リダイレクト |
| Webhook | HMAC-SHA256 を **raw body** に対して検証。不一致は 401 |
| 認証 | メール＋パスワード。パスワードは bcrypt。最低 12 文字 |
| 認可 | ロール（`staff` / `admin`）に基づく Policy。**画面の非表示と Policy の両方**で塞ぐ |
| CSRF | Laravel 標準。Webhook 受信のみ除外 |
| XSS | Blade のエスケープを既定とし、`{!! !!}` を使わない |
| SQL インジェクション | Eloquent / クエリビルダのバインドのみ。生 SQL の文字列連結を禁止 |
| 総当たり | 予約番号ごと 10分5回、IP ごと 10分30回（要件 7.2） |
| 列挙対策 | 照会失敗時、**文言も応答時間も分岐させない**（設計 8.3） |
| ログイン試行 | メールごと 10分5回。**デモアカウントのみ 10分30回に緩和**（下記）。監査ログに成功・失敗の別を記録 |
| ファイル公開 | `.env` と `storage` に web から到達しないことを段階0で確認 |
| 秘匿情報 | Shopify のトークン・SMTP 認証情報は `.env` のみ。リポジトリに含めない |

**デモアカウントのログイン制限を緩める理由。** 公開ページに記載したアカウントは
**全閲覧者が同じメールアドレスでログインする**。通常どおり10分5回で締めると、
誰かが5回打ち間違えた時点で以降10分間は誰も入れない。要件 7.2 が IP 制限を緩めたのと同じ理由で、
`users.is_demo` が立つアカウントだけ 10分30回とする。それ以外のアカウントは 10分5回のまま。

### 5.2 個人情報の扱い

本システムが保持する個人情報は**氏名・メールアドレス・電話番号**。

| データ | 保持期間 | 根拠 |
|---|---|---|
| `reservations` | 日次リセットで消える（デモ） | 要件 7.4 |
| `mail_logs`（本文・宛先を含む） | 90 日（**リセット対象外**） | 要件 7.4・設計 7.1 |
| `webhook_events`（`payload` を含む） | 90 日（**リセット対象外**） | 同上 |
| `audit_logs` | 90 日（**リセット対象外**、期間超過後は行削除） | 要件 7.4 |

**ログ系3テーブルを日次リセットの対象から外す。** ここを毎晩消すと 90 日の保持期間が
一度も意味を持たず、`logs:prune` も発火しない。**送信履歴と受信履歴を後から追えること**が
これらを持つ理由（設計 7章）なので、`audit_logs` と同じ扱いに揃える。

**デモとして公開する以上、シードに実在の個人情報を思わせる値を入れない**（要件 7.2）。

`audit_logs` は**個人情報を保存しない**方針で運用する。`changes` には
氏名・メール・電話・メール本文を含めず、必要な識別はハッシュ値で代替する。

保持期間を過ぎたものは、`mail_logs` / `webhook_events` については
**行を残したまま個人情報だけを消す**（件数の統計を壊さないため）。
対象は `mail_logs.body` と **`mail_logs.to`**、`webhook_events.payload`。
宛先を消し忘れるとメールアドレスだけが無期限に残るため、本文とあわせて必ず落とす。
`audit_logs` は保持期間超過分を行削除する。

### 5.3 やらないこと

WAF、IDS、ペネトレーションテスト、多要素認証は対象外。
デモ環境の規模と価値に対して過剰であるため。

## 6. ログ・監査・監視

### 6.1 ログの種類

| 種類 | 保存先 | 内容 |
|---|---|---|
| アプリケーションログ | `storage/logs`（日次ローテート・14日） | エラーと警告。障害の切り分けができる粒度 |
| 監査ログ | `audit_logs` | ログイン試行、予約の作成・修正・キャンセル、在庫更新、権限変更 |
| Webhook 受信ログ | `webhook_events` | 受信内容、処理状態、試行回数、失敗理由 |
| メール送信ログ | `mail_logs` | 宛先・件名・本文・送信状態・エラー |

**在庫を動かした操作は前後の値を残す**（設計 4.3）。ズレの原因追跡はここだけが頼りになる。

### 6.2 ログに書かないもの

パスワード、Shopify の API トークン、SMTP 認証情報。
`Log::` に配列をそのまま渡さず、必要な項目だけを明示的に書く。

### 6.3 監視

APM は導入せず、**管理画面のダッシュボードを監視画面として使う**。
外部サービスは死活監視の1本だけ使う（6.4）。

| ウィジェット | 見るもの | 異常の閾値 |
|---|---|---|
| Webhook 失敗件数 | 未処理・失敗の件数 | 1 件以上で要確認 |
| 在庫差分（`InventoryDrift`） | `Shopify在庫 + 確定予約数 ≠ 定員` の枠（`cache` から読む） | 1 件以上で要確認 |
| 本日の予約数 | 業務量の把握 | — |
| 直近の開催枠 | 埋まり具合 | — |

失敗ジョブ（`failed_jobs`）の件数も同ダッシュボードに出す。
**通知と日次確認の二段構え**にする。

| 検知対象 | 契機 | 頻度 |
|---|---|---|
| Webhook 処理の最終失敗 | ジョブの `failed` フック | 発生時 |
| メール送信の失敗 | ジョブの `handle()` 内（自動再送なしのため `failed` フックは使わない。設計 7.1） | 発生時 |
| 在庫差分 | `inventory:check` バッチ | 15 分ごと |

在庫差分だけはイベントで拾えない。Shopify の在庫を引いて初めて分かるため、
**定期チェックでしか検出できない**。在庫の取得は複数枠をまとめて1リクエストで引くため、
15 分間隔でも1日あたりの呼び出しは数百回に収まり、レート制限には当たらない。

**`InventoryDrift` ウィジェットは `inventory:check` の結果を `cache` から読む。**
画面表示のたびに Shopify を叩くと、複数人がダッシュボードを開いただけで
呼び出しが跳ね上がる。ウィジェットには**最終確認時刻を併記**し、
いつ時点の値を見ているのかが分かるようにする。

- 通知先: 管理者メール。1件1通、**同一対象は30分抑止**する
- 抑止状態は `cache` に持つ。`cache` テーブルは**日次リセットの対象に含めない**
  （毎晩消えると抑止が効かず、翌朝に同じ通知が並ぶ）
- 日次確認: ダッシュボードを 1 日 1 回確認し、通知漏れや抑止中の異常を拾う
- 異常時対応: 当日中に手動再実行し、解消できなければ `audit_logs` に対応内容を残す

**通知はメール1本に依存する。** SMTP 停止時は通知自体が届かないため、
その状態は日次確認と死活監視で拾う。通知経路を二重化するほどの規模ではない。

### 6.4 死活監視

cron が止まると、キュー消化も日次バッチも即時通知もまとめて止まる。
**止まったことを内部から知らせる手段がない**ため、ここだけ外部から見る。

- 公開エンドポイント `/health` を用意し、**最後に `schedule:run` が動いた時刻**を返す
- 最終実行から 10 分以上空いていたら 503 を返す
- 無料の外形監視サービスから 5 分間隔で叩き、応答が異常なら管理者へ通知する
- 個人情報や内部構成を含めない。返すのは状態と時刻だけ

これで「サーバーは生きているが cron だけ死んでいる」という、
この構成でいちばん気づきにくい状態を検知できる。

## 7. 運用

### 7.1 定常運用

| 頻度 | 作業 |
|---|---|
| 日次（自動） | デモリセット、締切・開催済み・無断欠席の更新、リマインド送信、ログ削除 |
| 随時（自動通知） | Webhook 失敗・在庫差分の通知受信と一次対応 |
| 日次（手動） | ダッシュボードで失敗件数と在庫差分を確認（通知漏れの検知） |
| 随時 | 失敗した Webhook・メール・在庫ジョブの再実行 |

自動処理はすべて `schedule:run` 1本の配下に置き、**`withoutOverlapping()` を必須**とする（要件 5.4）。

### 7.2 デプロイ

- **ゼロダウンタイム要件なし。** `migrate --force` 時の瞬断を許容する
- デプロイ手順は設計 11 章に従い、段階0で一度通し切る。**手動で1回成功させてから自動化する**
- 自動デプロイは GitHub Actions（`.github/workflows/deploy.yml`）で行う。
  **2026-08-06 時点では private リポジトリで Required reviewers が使えないため、
  トリガーは `workflow_dispatch`（手動実行）のみ。** リポジトリ public 化後に
  `push: branches: [main]` と承認ゲートを復元する（要件 11・設計 11章）
- マイグレーションは**後方互換を保つ方向のみ**（カラム追加・インデックス追加）。
  破壊的変更が必要な場合はデモリセットのタイミングに合わせる
- **破壊的変更を含むデプロイの前は、手で DB のバックアップを取る。**
  自動デプロイは日次バックアップ（4.3）以外の巻き戻し手段を持たない
- 転送は `rsync --delete` で行い、`.env` / `storage` / `public/storage` を除外する。
  **サーバー上にしか無いものを消さないこと**が除外リストの目的
- **公開リポジトリであるため、`pull_request` を契機に Secrets を使うジョブを作らない。**
  fork からの PR で秘密鍵が渡る経路を残さない

| Secret | 用途 |
|---|---|
| `DEPLOY_HOST` / `DEPLOY_USER` / `DEPLOY_PORT` | SSH の接続先（実ドメインを含むため Secret に置く） |
| `DEPLOY_PATH` | サーバー上のアプリケーションルート |
| `DEPLOY_PHP_BIN` | サーバーの PHP 8.3 系 CLI のパス（既定の `php` が 8.3 とは限らない） |
| `DEPLOY_SSH_KEY` | CI 専用の秘密鍵。開発者の常用鍵を使い回さない |
| `DEPLOY_KNOWN_HOSTS` | 接続先のホスト鍵。未設定時は都度 `ssh-keyscan` にフォールバックする |
| `DEPLOY_HEALTH_URL` | デプロイ後に応答を確認する URL（`/health`） |

### 7.3 デモ環境固有の要件

- デモアカウントは権限変更・削除・パスワード変更の対象外（Policy と非表示の両方で塞ぐ）
- `demo:reset` は**何度流しても同じ結果**になること（冪等）
- `demo:reset` は公開デモ環境（`APP_ENV!=production`）でのみ動くガードを持つこと
- リセットは **Shopify 在庫の書き戻しを含む**（要件 7.4）。
  書き戻し後に**在庫差分が0件であること**を合格基準とする（設計9）
- **リセット対象外**: `audit_logs` / `mail_logs` / `webhook_events` / `cache`（5.2・6.3）

## 8. 保守性

| 項目 | 基準 |
|---|---|
| 業務ロジックの置き場所 | `Actions` に集約。Filament のフォーム・ジョブ・コントローラに書かない |
| 状態遷移 | enum ＋ モデルのメソッド経由のみ。`status` の直接代入を禁止 |
| コーディング規約 | Laravel Pint（`laravel` プリセット）。CI で検査 |
| 静的解析 | PHPStan level 5 を目安に導入（段階5で有効化可否を判断。**未導入・判断保留**） |
| 依存 | Composer / npm ともにメジャーバージョンを固定 |
| ドキュメント | `docs/` に要件・設計・本書・運用手順を置き、実装と乖離したら実装側に合わせて更新 |

**「どこを直せばよいか1分で分かること」を保守性の判定基準にする。**
在庫の増減を追うときに `Actions` 2クラスだけ読めば済む状態を維持する。

## 9. テスト・品質

### 9.1 自動テスト

Feature テストで**壊れると業務が壊れる箇所**に絞る（設計 10章の6項目）。加えて本書の観点から次を追加する。

7. メール送信失敗時に業務処理が継続し、`mail_logs.status=failed` が残る
8. 手動登録で在庫減算成功後に DB 更新が失敗した場合、補償の在庫戻しが積まれる
9. Webhook payload で `line_item.id` が欠損している場合、受信は記録しつつ
   `webhook_events.status=failed` になり、予約を作らない

Shopify API は `Http::fake()` で差し替え、**実 API を叩くテストは書かない**。
GitHub Actions（`.github/workflows/ci.yml`）で実行する。**CI もローカルと同じ
`docker compose` 上の MySQL 8.0 で走らせる**（SQLite に替えない。16.2 と同じ理由）。
このワークフローは `workflow_call` で公開しており、デプロイの事前チェックとして再利用する。
**2026-08-05 時点で Feature テスト 44 件 + Unit 1 件（計 45 件）が通過。**

### 9.2 手動確認

| 対象 | 確認方法 | 合格基準 |
|---|---|---|
| C-1・C-2 | Lighthouse | **ユーザー補助 100** |
| 管理画面 | キーボード操作 | 主要操作がキーボードのみで完了し、フォームにラベルがある |
| 表示互換 | Chrome / Safari / Edge 最新、スマートフォン | レイアウト崩れがない |
| 復元手順 | バックアップからの復元 | 段階5までに一度成功させる |

### 9.3 完成判定との関係

要件 9 章の**シナリオ8項目が本番 URL で通ること**を機能面の完成とし、
本書の 9.1・9.2 を満たすことを非機能面の完成とする。**両方を満たして完成。**

## 10. アクセシビリティ・表示

| 対象 | 基準 |
|---|---|
| C-1・C-2 | Lighthouse ユーザー補助 100。ラベルの `for` 関連付け、`aria-describedby` と `role="alert"`、送信後のフォーカス移動、コントラスト比の確保 |
| 管理画面 | 数値目標を置かない。キーボード操作とラベルの有無を確認するまで |

**測った画面がどれかを公開ページに明記する。** 第1弾のスコアと並べる際に、
管理画面まで 100 だと誤読させないため（要件 7.3）。

## 11. 移行・廃止

- 初期データはシードで投入する。既存システムからの移行は対象外
- 本システムを止める場合、Shopify 側のバリアント在庫が残るため、
  **停止前に開催枠の在庫を手動で調整する**運用とする
- Webhook の購読解除を停止手順に含める
