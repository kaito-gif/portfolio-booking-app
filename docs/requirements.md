## 1. 概要

### 1.1 目的

日本茶ストア（架空ブランド `chanoka`）が開催する**ワークショップの予約を管理する**
システムを構築する。参加権の販売と決済は既存の Shopify ストアが担い、本システムは
Shopify が持たない予約業務（当日の受付、電話予約、キャンセル、名簿の出力）を受け持つ。

### 1.2 このシステムを作る理由（ポートフォリオとしての目的）

開発・システムの相談を受けた場に出す成果物として作る。想定する読み手は**非エンジニアの
事業者**で、画面を30秒眺めて「うちの困りごとに近い」と思えるかどうかで価値が決まる。
したがって技術デモではなく、**業務でそのまま使える形に見えること**を優先する。

### 1.3 用語

| 用語 | 意味 |
|---|---|
| 講座 | ワークショップの種類。「茶の淹れ方講座」など |
| 開催枠 | 講座の特定の日時の回。「11月3日14時の回・定員8名」 |
| 予約 | ある開催枠に対する1件の申し込み |
| 1予約=1席 | このシステムでは予約1件を必ず1席として扱う（複数人数予約は対象外） |
| 予約番号 | 顧客が照会に使う識別子 |

## 2. 対象範囲

### 2.1 対象とするもの

- Shopify での参加権購入をきっかけとした予約の自動登録
- 電話・対面で受けた予約の手動登録
- 顧客自身による予約の照会とキャンセル
- 管理者による予約の一覧・検索・修正・CSV 出力
- 当日の参加者名簿の出力とチェックイン
- 開催枠と講座の登録・編集
- 予約確定・リマインド・キャンセル完了の各メール送信

### 2.2 対象としないもの

**作れないのではなく、作らないと判断したもの。** 実装中の歯止めであり、
公開ページで設計判断として説明する材料でもある。

| 対象外 | 理由 |
|---|---|
| 決済 | Shopify のカートに任せる。二重に持つ理由がない |
| 返金処理 | キャンセル時の返金は Shopify 管理画面で人が行う |
| 顧客アカウント | 予約番号とメールでの照会に留める。会員管理・パスワード再発行・退会が丸ごと不要になる |
| 時間指定型の予約 | 枠固定型に限定する。空き枠計算が本格化し範囲が数倍になる |
| スタッフの割り当て・シフト管理 | 1事業者・少人数の運用を想定 |
| 複数拠点 | 同上 |
| 多言語 | 日本語のみ |
| リアルタイム通知 | 画面の更新で足りる |
| 定期予約・回数券 | 単発の講座のみ |
| 外部カレンダー連携・SMS 通知 | メールで足りる |
| Shopify 側で在庫を直接編集した場合の同期 | 検知も補正もしない。運用で在庫は本システムから操作する |

## 3. 利用者と権限

| ロール | 認証 | できること |
|---|---|---|
| 顧客 | なし（予約番号＋メールで照会） | 自分の予約の閲覧とキャンセル |
| スタッフ | ログイン | 予約の閲覧・手動登録・修正・キャンセル、当日リスト、CSV 出力 |
| 管理者 | ログイン | スタッフの全権限に加え、講座と開催枠の登録・編集、ユーザー管理 |

顧客にアカウントを持たせない。照会には予約番号とメールアドレスの一致を要求する。

## 4. 業務フロー

### 4.1 Shopify 経由の予約（主たる導線）

```
[顧客] Shopify で参加権を購入（開催枠 = 商品バリアント / 定員 = 在庫数）
   ↓ 決済完了。Shopify が在庫を1減らす
[Shopify] Webhook orders/create を送信
   ↓
[本システム] 署名を検証 → 重複を排除 → キューに積んで即座に 200 を返す
   ↓
[本システム] 予約を登録し、予約番号を発行 → 確定メールを送信
   ↓
[管理者] 管理画面で予約を確認。前日にリマインドが自動送信される
   ↓
[当日] 当日リストを出力し、チェックインする
```

売り切れの制御は Shopify の在庫が担う。**本システムは定員超過の判定を持たない。**
これにより二重管理が発生しない。
在庫は Shopify の**単一ロケーション**で管理する前提とし、本システムが増減する対象も
そのロケーションに固定する。

**1注文に複数の席が含まれる場合。** カートは数量2以上でも購入でき、複数の開催枠を
まとめて買うこともできる。1予約=1席のため、注文の `line_items` をすべて走査し、
**開催枠として登録済みのバリアントについて、数量の数だけ予約を作る**。
予約番号は席ごとに発行する。確定メールは注文単位で1通にまとめ、
本文にすべての予約番号を並べる。宛先が同じメールに複数通届くのを避けるため。

開催枠に紐づかないバリアント（茶葉などの物販）は無視する。ワークショップの
参加権と通常商品が同じ注文に混ざっても、予約は参加権の分だけ作られる。

### 4.2 電話・対面での予約（手動登録）

管理画面から予約を直接登録する。このとき **Shopify 側の在庫を1減らす**。
減らさないと Shopify から追加で売れてしまい、定員を超える。
1予約=1席のため、手動登録でも人数入力は持たない。

### 4.3 キャンセル

顧客が照会画面から、または管理者が管理画面から実行する。
実行時に **Shopify 側の在庫を1戻す**。返金は行わず、別途対応する旨をメールに記載する。

キャンセル可能な期限は**開催日の前日23時59分まで**とする。それ以降は管理者のみ操作できる。

**返金時に在庫を戻さない。** Shopify 管理画面で返金する際、既定では商品が
在庫へ戻る。本システムが既に1戻しているため、そのまま返金すると在庫が二重に増える。
返金操作では復元のチェックを外す運用とし、この点を管理画面のキャンセル完了画面に注記する。

## 5. 機能要件

### 5.1 画面一覧

| # | 画面 | 対象 | 概要 |
|---|---|---|---|
| C-1 | 予約照会 | 顧客 | 予約番号とメールを入力する |
| C-2 | 予約詳細 | 顧客 | 内容の確認とキャンセルの実行 |
| A-1 | ログイン | 管理 | メールとパスワード |
| A-2 | ダッシュボード | 管理 | 本日の予約数、直近の開催枠と埋まり具合、Webhook の失敗件数 |
| A-3 | 予約一覧 | 管理 | 検索・絞り込み・ページング・CSV 出力 |
| A-4 | 予約詳細／手動登録 | 管理 | 新規登録・修正・キャンセル |
| A-5 | 当日リスト | 管理 | 印刷向けの名簿。チェックイン |
| A-6 | 開催枠一覧 | 管理 | 日付での絞り込み |
| A-7 | 開催枠の登録・編集 | 管理 | 日時・定員・Shopify バリアントの紐付け |
| A-8 | 講座一覧・編集 | 管理 | 講座名・説明・所要時間 |
| A-9 | ユーザー管理 | 管理者のみ | スタッフの追加と権限変更 |

### 5.2 主要機能の詳細

**予約一覧（A-3）** — 開催日、講座、予約状態、氏名・メール・予約番号の部分一致で
絞り込める。1ページ50件のページング。表示中の絞り込み条件のまま CSV に出力できる。
CSV の文字コードは Excel でそのまま開けるよう UTF-8 BOM 付きとする。

**当日リスト（A-5）** — 指定日の開催枠ごとに、参加者の氏名・電話番号・
チェックイン欄を並べる。印刷用のスタイルを用意する。画面上でチェックインを記録できる。

**手動登録（A-4）** — 開催枠を選び、氏名・メール・電話を入力する。
登録と同時に Shopify の在庫を減らす。**在庫の更新に失敗した場合は予約を登録しない。**
1予約=1席のため、1件登録で在庫を1減らす。

**開催枠の登録（A-7）** — 講座・開始日時・定員・Shopify のバリアントIDを設定する。
状態は「下書き」「受付中」「締切」「中止」「開催済み」。
「受付中」から「締切」への遷移は日次バッチが自動で行い、管理者は任意の時点で
手動でも締め切れる。締切後は Shopify 経由の予約（Webhook）が届いても
予約は作らず、`webhook_events` に理由を記録して管理画面に表示する。

### 5.3 メール

| 種別 | 送信契機 |
|---|---|
| 予約確定 | Webhook からの登録時（注文単位で1通）、および手動登録時 |
| リマインド | 開催日の前日朝（日次バッチ） |
| キャンセル完了 | キャンセル実行時 |

いずれも予約番号と照会 URL を含める。

### 5.4 バッチ・非同期処理

| 処理 | 実行間隔 |
|---|---|
| キューの消化 | 毎分 |
| 在庫差分の検出と通知 | 15分ごと |
| リマインドメールの送信 | 日次（朝） |
| 締切への状態更新 | 日次（深夜0時。前日23時59分を過ぎた開催枠が対象） |
| 開催済みへの状態更新 | 日次 |
| 無断欠席への状態更新 | 日次（開催済みへの更新より後） |
| デモデータの初期化 | 日次（深夜） |

cron からは Laravel のスケジューラを1本だけ呼び、各処理はその中に登録する。
毎分実行のため、**多重起動の防止（`withoutOverlapping`）を必須とする。**
前の実行が終わらないうちに次が走ると、メールの二重送信や在庫の二重更新につながる。

### 5.5 Shopify 連携

**受信** — `orders/create` の Webhook を受ける。HMAC 署名を検証し、
`X-Shopify-Webhook-Id` で重複を排除する。**Shopify は同じ Webhook を複数回送るため、
冪等性の担保は必須。** 受信内容は処理前に記録し、失敗しても再処理できるようにする。
Webhook には5秒以内に 200 を返す必要があるため、本処理はキューに逃がす。
`line_item.id` は冪等性に必要な必須項目とし、欠損している payload は
**仕様違反として失敗扱い**にする（受信自体は記録し、処理側で `failed` に落とす）。

**送信** — 手動登録時に在庫を1減らし、キャンセル時に1戻す。API のレート制限に
備えてリトライを実装する。対象は単一ロケーションに固定し、ロケーションIDを
設定値として保持する。

**再処理** — Webhook 処理失敗時は指数バックオフで最大5回まで自動リトライし、
それでも失敗したものは失敗キューとして管理画面に表示して手動再実行できるようにする。
試行回数と次回実行時刻は `webhook_events` に持たせ、`A-2` の失敗件数はここから数える。

**対象外** — 注文のキャンセル・返金・編集の Webhook は購読しない。Shopify 側で
注文を取り消した場合は、管理画面から予約もキャンセルする運用とする。
購読を増やすと、どちらが在庫を戻したのかを追う処理が必要になり範囲が広がるため。

## 6. データ要件

### 6.1 エンティティ

| テーブル | 主な項目 |
|---|---|
| `workshops`（講座） | 名称、説明、所要時間、Shopify 商品ID |
| `slots`（開催枠） | 講座ID、開始日時、定員、状態、Shopify バリアントID |
| `reservations`（予約） | 開催枠ID、予約番号、氏名、メール、電話、状態、Shopify 注文ID、チェックイン日時 |
| `users`（管理ユーザー） | 氏名、メール、パスワード、権限、デモ用フラグ |
| `webhook_events`（受信ログ） | Shopify の Webhook ID、種別、受信日時、本文、処理状態、試行回数、次回実行時刻、失敗理由 |
| `audit_logs`（監査ログ） | 操作者、操作種別、対象、内容、IPアドレス、日時 |

### 6.2 状態遷移

予約は「確定」から「キャンセル済み」「参加済み」「無断欠席」へ遷移する。
無断欠席は、チェックインされないまま開催終了日時を過ぎた確定予約を日次バッチで更新する。

開催枠は「下書き → 受付中 → 締切 → 開催済み」と進み、任意の時点で「中止」にできる。
**「受付中」から「開催済み」へ直接は進めない。** 必ず「締切」を経由する。
締切を挟まないと、その間に Shopify から届いた予約の扱いが決まらないため。
締切への更新は日次バッチが先に走り、開催済みへの更新はその後に回す。

### 6.3 その他

予約番号は推測できない形式とし、連番は用いない。照会にメールアドレスの一致を
求めるとはいえ、連番だと総当たりの足がかりになる。

日時はすべて JST で扱う。多言語・多拠点を対象外としているためタイムゾーンは固定する。

`slots.capacity`（定員）は表示と初期設定のために保持する参照値とし、売り切れ判定の
実体は Shopify 在庫を正とする。運用上の整合は「定員=初期在庫」で揃えて開始する。

## 7. 非機能要件

### 7.1 想定規模

1事業者・月間の予約件数は数百件・同時利用者は数名を想定する。
性能上の工夫を要する規模ではない。

### 7.2 セキュリティ

Webhook の署名検証、CSRF 対策、権限に基づく認可、照会画面への総当たり対策を行う。
`.env` と `storage` を web から到達させない。

総当たり対策は**予約番号ごとに10分で5回まで**を基本とし、IP 単位では10分で30回までと
緩めに置く。触って試せるデモである以上、IP だけで絞ると同じ回線から見ている
複数の閲覧者を巻き込んで締め出してしまうため。
**デモとして公開する以上、投入するシードデータに実在の個人情報を思わせるものを含めない。**

### 7.3 表示・アクセシビリティ

最新版の Chrome・Safari・Edge と、スマートフォンのブラウザに対応する。

第1弾のデモストアで Lighthouse のユーザー補助 100 を出しているため、
**自分でマークアップを書く顧客向け画面（C-1・C-2）は 100 を目標とする。**

管理画面は Filament の既製UIを使うため、マークアップを全面的には制御できない。
こちらは数値目標を置かず、**キーボードのみで主要な操作ができること・フォームに
ラベルがあることを確認する**までとする。第1弾のスコアと並べて示す際は、
どの画面を測った数字なのかを明記する。

### 7.4 運用

デモ公開のため、日次でデータを初期状態に戻す。管理者・スタッフのデモアカウントを
公開ページに記載し、**触って試せる運用を優先**する。

監視は手動確認だけに依存しない。**Webhook 処理失敗または在庫差分の検知時に管理者へ即時通知**
し、通知漏れの補完として日次でダッシュボードを確認する。異常があれば当日中に手動再実行する。

**バッチが止まったこと自体は外部から監視する。** 通知も日次処理も同じ cron に乗っているため、
cron が止まると異常を知らせる手段ごと失われる。死活確認用のエンドポイントを用意し、
外形監視サービスから定期的に確認する。

**日次リセットは Shopify の在庫も初期値へ書き戻す。** 手動登録とキャンセルは
Shopify の実在庫を増減するため、自システムの DB だけ戻すと、閲覧者が減らした在庫が
第1弾のデモストアに残り続ける。開催枠に紐づくバリアントの在庫を設定し直す。

書き戻す値は `slots.capacity` そのものではなく、**`capacity` から初期投入した
予約の件数を引いた値**とする。シードは各枠にあらかじめ予約を入れるため、
定員そのものに戻すと在庫と予約数の合計が定員を超え、**リセット直後から
在庫差分の警告が全枠に出る**。

**デモアカウントは自壊しないよう保護する。** `users` のデモ用フラグが立った
アカウントは、権限変更・削除・パスワード変更の対象外とする。保護しないと、
閲覧者が管理者アカウントの権限を落とした時点で、翌日のリセットまで誰もログインできない。

ログイン試行・予約の作成と修正・キャンセル・在庫更新・権限変更は監査ログに残す。
**監査ログ・メール送信履歴・Webhook 受信履歴は日次リセットの対象外**とし、
いずれも90日で古いものから削除する。リセットで消すと、デモ環境で何が起きたのかを
後から追えなくなる。

監査ログ（`audit_logs`）は**氏名・メール・電話・メール本文などの個人情報を保存しない**
方針とし、保持期間超過後は行ごと削除する。メール送信履歴と Webhook 受信履歴は、
件数の統計を壊さないため行を残したまま個人情報を削除する。

障害の切り分けができる程度のログを残す。

## 8. 制約

**実行環境は Xserver の共用レンタルサーバー（スタンダードプラン）。**
VPS ではないため次の制約がある。

- **常駐プロセスを立てられない。** supervisor が使えないため、キューは cron から
  `queue:work --stop-when-empty` を毎分呼ぶ方式にする。最大1分の遅延が生じるが、
  予約処理では実害がない
- ドキュメントルートをサブドメインの設定で `public` に向ける必要がある
- **PHP のバージョンをサーバーパネルで確認・変更しておく。** Laravel と Filament は
  いずれも比較的新しい PHP を要求するため、既定のままだと段階0で止まる。
  `storage:link` が張れることも段階0のうちに確かめる
- Vite のビルドはローカルで行い、成果物をアップロードする
- SSH は初期状態で無効。サーバーパネルで有効化し公開鍵を登録する

連携先の Shopify ストアは開発ストアで、**パスワード保護を外せない。**
Webhook はパスワードと無関係に届くため連携に支障はないが、購入画面を見てもらうには
ストアパスワードが要る。**本システムの管理画面は独立して公開できるため、
見せ場は管理画面側に置く。**

## 9. 完成の定義

機能単位ではなく**シナリオ単位**で判定する。機能で切ると「あと1つ足りない」が
続いて終わらない。以下がデモ環境で通った時点を完成とする。

1. Shopify で参加権を購入すると、予約が自動で登録され、確定メールが届く
2. 管理画面で当日リストを出力できる
3. 電話予約を手動で登録でき、Shopify の在庫が1減る
4. 顧客が自分でキャンセルでき、Shopify の在庫が1戻る
5. 予約一覧を絞り込んだ状態で CSV に出力できる
6. 数量2で購入すると予約が2件登録される
7. 日次リセットの翌日、DB と Shopify の在庫がどちらも初期状態に戻っている
8. 以上が本番 URL のデモアカウントで一通り操作できる

## 10. 開発の段階

各段階の終わりに、見せられるものが残るように並べる。

| 段階 | 内容 | 終了時に見せられるもの |
|---|---|---|
| 0 | デプロイ経路の確立 | 本番 URL に空の Laravel が表示される |
| 1 | 管理画面（Shopify 抜き） | 枠と予約を手で作れる。業務システムとして既に見せられる |
| 2 | Shopify Webhook の受信 | 購入から予約が自動で入る |
| 3 | メール・CSV・当日リスト | 業務が一周する |
| 4 | キャンセルと在庫の戻し | 双方向連携。Webhook を受けるだけの実装との差が出る |
| 5 | デモ公開の仕上げ | シード・日次リセット（Shopify 在庫の書き戻しを含む）・保護つきデモアカウント |

**段階0を最後に回さない。** まとめてデプロイすると必ず詰まる。

規模が重いと感じた場合に削る順番は、講座マスタ（開催枠に統合する）、
次にリマインドメール。**ダッシュボードは実装が軽いわりに第一印象に効くので残す。**

管理画面の実装方式は **Filament** を採用する。短期間で業務画面を成立させることを優先し、
必要な差分（予約フロー、Shopify 連携、当日リスト、CSV 出力）で独自実装の見せ場を作る。
